# Pipeline delivery (#6) — what landed and what it needs

The SSE transport, the cross-request approval write path, and the tests behind
them are implemented in `src/server/pipeline-delivery/`. The approval POST is
mounted. The SSE GET is implemented and tested but deliberately **not mounted**
because its stage provider does not exist on `main`.

## Mounted route (frag2win review)

| Path | File |
|---|---|
| `POST /api/pipeline/:experimentId/approve` | `src/routes/api/pipeline/$experimentId/approve.ts` |

`src/routeTree.gen.ts` was regenerated by the TanStack Start router plugin.
The file is a three-line adapter: it forwards `{ request, params }` to
`handlePipelineApproval` and returns the raw `Response`.

The handler is authenticated with #4's `readCurrentUser`, authorized against
`workspace_members` with #4's `enforceWorkspaceMembership`, requires a
same-origin `Origin` header, and writes exactly one decision through #37's
`decideApproval`. The decision is bound to the persisted
`approval.requested` seq and records the verified actor. It never runs a
stage, a script or a sandbox.

## The GET is not mounted

`GET /api/pipeline/:experimentId` needs a stage provider to reach the approval
gate: PLAN_EXPERIMENT produces the `ExperimentSpec` the human is asked to
approve. On `main` that code does not exist.

| Dependency | File state on `main` | Export #6 can consume today | What #6 needs from it |
|---|---|---|---|
| #23 planner | `src/server/planner.ts` is absent | None | Produce and validate the `ExperimentSpec` |
| #24 E2B runner | `src/server/runner.ts` exports only the frozen `ExperimentRunner` interface | `ExperimentRunner` (type only) | A concrete implementation: `run(spec, onStdout)` and `cancel(sandboxId)` |
| #25 evaluator | `src/server/evaluate.ts` is absent | None | Compute the verdict from `spec.criteria` and `result.metrics` |
| #7 integration seam | `src/server/pipeline.ts` is absent | None | **Not required by #6.** This is the graph write-back seam (`onRunComplete(run: RunRow)`) for a finished run's result node, run node and produced edge. It is a later graph hook, not part of the SSE/claim/gate lifecycle. |

PR #43 is not a dependency of this branch and must not be imported or based on
until its review blockers are fixed and it merges. Nothing in
`src/server/pipeline-delivery/` imports `planner`, `runner`, `evaluate`,
`pipeline`, or any file from PR #43; the only runtime dependency is the frozen
`PipelineStages` interface this branch owns.

Mounted GET would have to return a fake stage outcome, which the product
forbids. Instead, the production handler returns `503
PIPELINE_STAGES_UNAVAILABLE` **before claiming** when no provider is supplied,
and the route file is omitted. A reconnect for an experiment that already has
a claim still works without a provider, because it only replays durable
events.

## The seam a real provider implements

`src/server/pipeline-delivery/stages.ts`:

```ts
export interface PipelineStages {
  plan(context: PipelineStageContext): Promise<{ spec: ExperimentSpec }>
  execute(
    context: PipelineStageContext,
    spec: ExperimentSpec,
  ): Promise<{ runId: string | null }>
}
```

`PipelineStageContext` carries the experiment and workspace ids, the verified
actor id, an abort `signal` (client disconnect or the 240 s budget), and
`emit`. The provider emits its own `stage.*`, `agent_task.recorded`,
`node.upserted`, `edge.upserted`, `run.*` and `verdict.computed` events through
`emit`; the transport owns claims, gate opening, approval polling, replay,
heartbeats, the budget and the terminal event.

Rules the provider must keep:

- `plan` returns a spec whose `claimNodeId` is the experiment's claim node
  (the database rejects a gate with a mismatched spec).
- `execute` is called only after an approval, with the **offered** spec from
  the gate, never a newer plan.
- A budget abort must stop work and let the transport emit `run.timeout` (when
  a run had started) followed by `pipeline.failed`.
- Writing result/run nodes and the `produced` edge is #7's job, not the
  transport's.

## Coupling the GET once a provider exists

The GET route is the same three-line adapter. When a real `PipelineStages`
exists, add `src/routes/api/pipeline/$experimentId.ts`:

```ts
import { createFileRoute } from '@tanstack/react-router'
import { createProductionPipelineHandlers } from '../../../server/pipeline-delivery/production'
import { productionPipelineStages } from '../../../server/pipeline' // #7 / runtime adapter

export const Route = createFileRoute('/api/pipeline/$experimentId')({
  server: {
    handlers: {
      GET: async ({ request, params }) => {
        const handlers = await createProductionPipelineHandlers({
          stages: productionPipelineStages,
        })
        return handlers.stream(request, params)
      },
    },
  },
})
```

Then regenerate the route tree (`pnpm build` or the dev server). The exact
name and location of `productionPipelineStages` belong to the provider owner;
the only contract is the `PipelineStages` interface above.

## Semantics implemented

- **One claim per experiment, ever.** `claimExecutionStart` is the only
  authorization to start. A reconnect, a concurrent GET, or a GET after expiry
  observes the existing claim and becomes a follower.
- **Last-Event-ID replay.** Replay is strictly `seq > lastEventId`, with the
  cursor validated against the persisted head before the stream starts.
- **Cross-request approval.** The stream polls `experiments.approval_state`
  every 500 ms; the POST commits in its own transaction. The stream then
  replays the persisted `approval.resolved` event with its real seq.
- **Rejection cancels.** A rejected decision emits `pipeline.cancelled`
  (`reason: 'rejected'`) and never calls `execute`.
- **240 s budget, 15 s heartbeat.** Defaults are the #33 primitives; tests
  inject shorter values. Budget expiry emits `run.timeout` when a run had
  started, then `pipeline.failed`; the terminal append closes the claim.
- **Terminal semantics.** Only the claim owner appends a terminal event. A
  follower that runs out of budget closes with a comment and fabricates
  nothing.

## Tests

`src/server/pipeline-delivery/delivery.integration.test.ts` runs the real
handlers against a real Postgres database (committed migrations, real
constraints and transactions) and covers: cross-request approve, rejection
cancellation, concurrent GET claiming once, reconnect replay, auth/member
denial (anonymous, non-member, member of another workspace), origin guards,
gate-seq/actor binding, body validation, wait timeout, execute timeout, and
"no provider means 503 with no claim written".

The stage provider in `test-support/fixture-stages.ts` is **test-only and
disclosed**. It emits deterministic pipeline events and writes no `runs`,
`nodes` or `edges` rows. No production path imports it.

Run against a disposable pgvector database:

```bash
TEST_DATABASE_URL=postgresql://... \
  pnpm exec vitest run src/server/pipeline-delivery
```

Without `TEST_DATABASE_URL`, the integration suite skips and the rest of
`pnpm test` is unaffected.
