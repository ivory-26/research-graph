# Pipeline delivery (#6) — what landed and what it needs

The SSE transport, the cross-request approval write path, the real stage
provider and the mounted routes are implemented in
`src/server/pipeline-delivery/`. Both endpoints are live:

| Method | Path | File |
|---|---|---|
| `GET` | `/api/pipeline/:experimentId` | `src/routes/api/pipeline/$experimentId.ts` |
| `POST` | `/api/pipeline/:experimentId/approve` | `src/routes/api/pipeline/$experimentId/approve.ts` |

Both route files are three-line adapters. They forward `{ request, params }` to
the framework-free handlers and return the raw `Response`. The behaviour lives
in the delivery modules so it can be tested against a real database without a
router. `src/routeTree.gen.ts` was regenerated by the TanStack Start plugin.

The approval POST is authenticated with #4's `readCurrentUser`, authorized
against `workspace_members` with #4's `enforceWorkspaceMembership`, requires a
same-origin `Origin` header, and writes exactly one decision through #37's
`decideApproval`. The decision is bound to the persisted `approval.requested`
seq and records the verified actor. It never runs a stage, a script or a
sandbox.

## The production stage provider

`src/server/pipeline-delivery/production-stages.ts` implements the
`PipelineStages` port with the modules that landed in #23/#24/#25:

| Stage | Real work |
|---|---|
| `PLAN_EXPERIMENT` | Loads `experiments.spec` and applies `validateExperimentSpec` from `src/server/planner.ts`. The planner validates; it does not generate, so this provider never invents a plan. An invalid stored plan fails the pipeline before a gate opens. |
| `EXECUTE` | Inserts the `runs` row (frozen `spec`, `status = running`), emits `run.started`, then calls the real `E2BRunner` from `src/server/runner.ts`. The measured result updates the row and becomes `run.succeeded` / `run.failed`. |
| `EVALUATE` | Calls `evaluateAndExplainExperiment` from `src/server/evaluate.ts`. `evaluateExperiment` computes the verdict before the model call; the model only writes the explanation. The verdict and checks are persisted back to the run and emitted as `verdict.computed`. |

Rules the provider keeps:

- **Genuine stages only.** It does not run or emit `INGEST_SOURCE`,
  `EXTRACT_CLAIMS` or `PROPOSE_EDGES`. Those stages produced the graph and the
  experiment row before this request; replaying their events here would be
  fiction.
- **The approved plan is the executed plan.** `execute` receives the gate's
  `offeredSpec` from the transport, never a re-read of `experiments.spec`.
- **The run is durable before the sandbox exists.** A provider crash leaves a
  `running` row with the exact approved spec rather than no record.
- **No raw provider text on the wire.** A typed runner error keeps sandbox
  output; any other runner exception is logged and replaced by a generic
  sentence before it is persisted or streamed. `PipelineStageError` carries a
  product-authored `safeMessage` for stage refusals.
- **Cancellation reaches the sandbox.** The provider listens to the transport
  signal (client disconnect or the 240 s budget) and calls `runner.cancel` on
  every live sandbox the E2B runner reports. The run row records why it
  stopped: `timeout` only when the budget signal fired, `cancelled` when the
  request or the stream consumer went away.
- **Every model call is recorded.** The evaluator's `callModel` writes one
  `agent_tasks` row per attempt, success or failure. The row it returns is
  also emitted as `agent_task.recorded`, and its id is the `taskId` on
  `stage.finished` for `EVALUATE`. A failed attempt is persisted and logged
  but not emitted: `callModel` throws without returning that row.

What the provider deliberately does not do:

- It does not write result/run graph nodes or the `produced` edge. That is
  `src/server/pipeline.ts` (#7), which has not landed. The run row and the
  durable events are the record this layer owns.
- It does not stream `run.stdout` chunks. The transport's only write path is
  the durable event log, so per-chunk stdout would create one row per line;
  `runs.stdout` is the durable record.

## Semantics implemented

- **One claim per experiment, ever.** `claimExecutionStart` is the only
  authorization to start. A reconnect, a concurrent GET, or a GET after expiry
  observes the existing claim and becomes a follower.
- **Last-Event-ID replay.** Replay is strictly `seq > lastEventId`, with the
  cursor validated against the persisted head before the stream starts.
- **Cross-request approval.** The stream polls `experiments.approval_state`
  every 500 ms; the POST commits in its own transaction. The stream then
  replays the persisted `approval.resolved` event with its real seq.
- **Rejection cancels.** A rejected decision emits `pipeline.cancelled`
  (`reason: 'rejected'`) and never calls `execute`.
- **240 s budget, 15 s heartbeat.** Defaults are the #33 primitives; tests
  inject shorter values. Budget expiry emits `run.timeout` when a run had
  started, then `pipeline.failed`; the terminal append closes the claim.
- **Caller-side deadline.** `openPipelineStream` races the stage runner against
  the budget/abort signal: when the budget fires it stops the heartbeat,
  replays committed events, appends `run.timeout` (when a run had started) and
  one `pipeline.failed`, delivers them, and closes the response without waiting
  for a stage that ignores `signal`. `emit` refuses everything after the
  deadline.
- **Terminal semantics.** Only the claim owner appends a terminal event. A
  follower that runs out of budget closes with a comment and fabricates
  nothing.
- **Failure text.** `pipeline.failed.error` and `run.failed.error` are generic
  or product-authored; provider/driver detail stays in the server log.

## Tests

`pnpm test` runs the `node:test` transport primitives and the Vitest suite.
The pipeline-delivery integration files are skipped unless `TEST_DATABASE_URL`
names a disposable Postgres server with `CREATEDB`:

- `delivery.integration.test.ts` — transport lifecycle with a disclosed fixture
  provider: cross-request approve, rejection, concurrent claiming, reconnect,
  auth/member denial, origin guards, gate-seq/actor binding, body validation,
  budget expiry before and during execution, non-cooperative stages, error
  sanitization, and "no provider means 503 with no claim written".
- `production-stages.integration.test.ts` — the real provider over real
  Postgres: planner validation of the stored plan, run-row persistence, the
  computed verdict, the recorded `explain_gap` task, invalid-plan failure,
  runner-failure sanitization, rejection with no run, and budget expiry that
  cancels the live sandbox and marks the run `timeout`.
- `route.integration.test.ts` — the actual mounted route modules, called with
  real `Request` objects: cross-request approve and reject, reconnect replay
  without a second execution, and consumer cancellation killing the sandbox.
  The real `E2BRunner` runs against an in-memory `e2b` sandbox; `callModel` and
  the Neon client are the only other replaced boundaries. The database, SQL,
  constraints, planner, runner logic and evaluator are real.

`test-support/production-fixtures.ts` holds the valid plan, the deterministic
runner and the recording model call. No production path imports it.

Run against a local disposable pgvector container (the password is generated,
not a literal, so a committed snippet does not trip secret scanners):

```bash
TEST_PG_PASSWORD="$(openssl rand -hex 16)"
docker run --rm -d --name rg-test-pg \
  -e POSTGRES_PASSWORD="$TEST_PG_PASSWORD" -p 127.0.0.1:55432:5432 \
  pgvector/pgvector:pg18

TEST_DATABASE_URL="postgresql://postgres:$TEST_PG_PASSWORD@127.0.0.1:55432/postgres" \
  pnpm exec vitest run src/server/pipeline-delivery
```

`TEST_DATABASE_URL` names a **server**, not a database the suite may modify.
The harness creates a uniquely named `rg_test_*` database on it, migrates and
resets only that database, and drops only that database when the suite ends.
The database named in the URL is never migrated, truncated or dropped. The
host must be loopback unless `TEST_DATABASE_ALLOW_REMOTE=1` is set explicitly
for a disposable CI server. `test-support/pg.ts` holds the checks;
`test-support/pg-safety.test.ts` covers them without a connection.

## What is still missing

- **#7 graph write-back.** A completed run does not yet become result/run nodes
  plus the `produced` edge. That is the one integration seam #6 does not own.
- **Live E2B verification.** This suite uses a deterministic in-memory sandbox;
  a credentialed run against the pinned template is still the acceptance step
  for the sandbox path. The runner itself is #24's verified implementation.
- **Live Gemini explanation.** Without a provider key the evaluator logs the
  failed `explain_gap` call (with its `agent_tasks` row) and keeps the
  deterministic verdict. A live call is not required for the verdict.
- **In-flight work is not rolled back.** Cancellation kills the sandbox and
  refuses later `emit` calls, but a database write already in flight when the
  deadline fires may still commit. The durable event log stays ordered.
- **A terminal is only as durable as the database.** If the terminal append
  fails, the response still closes but no terminal row exists; the claim then
  expires on its lease and ADR 0003 applies (the run is lost).
